Claims and merge: collisions, not locks.

A file claim tells the room who is editing what. It never blocks a write. When two agents do touch one path, Rigel shows base, ours and theirs, and lands the resolution through the same journal as every other patch.

Why claims are advisory

A hard lock turns one slow agent into a stopped session, and a crashed agent into a file nobody can edit. Rigel chooses the opposite failure: a stale claim is reported, not enforced, and it is never released automatically. The user can see who claimed the path, when the heartbeat stopped, and decide what to do.

That also means a claim is not a safety boundary. The enforcement is the command gate and the reviewer; the claim is information. Both surfaces are needed, and neither is allowed to pretend it is the other.

The claim lifecycle

  1. Acquire records the agent, session, path and a heartbeat.
  2. Heartbeat moves the clock while the agent is still working.
  3. Release writes a tombstone rather than deleting the row, so the history of who held what survives.
  4. Expiry is 24 hours. An expired row is stale evidence, not an automatic release.

The same three verbs are exposed twice: as CLI commands and as MCP tools, so a harness that is not the native agent can participate in the room. 

rigel claim list
rigel claim release crates/rigel-core/src/agent/providers.rs
rigel who

The CLI and the MCP server read the same rows. A claim taken in one surface is visible in the other without a sync step.

Attribution: the watcher

A 250 ms watcher hashes changed files and compares them with the session’s claim and agent state. A change names its writer when the evidence is unambiguous. When it is not, the row says ambiguous instead of guessing a name.

If a claimed path moves under someone else, the watcher records a conflict. That record is what the diff surface opens; it is not a message that disappears after a toast.

Design choice: attribution is evidence, not blame. A missing link is printed as “unknown” with the reason, never filled in from the nearest agent.

The diff surface

Diff is one place for every change the session touched. The conflict strip shows both names and both hashes; unverified counts are shown next to the files they affect. Each patch can be reverted once it has been applied.

The three versions

Opening a conflict renders base, ours and theirs. The merged result is an editable file; saving it writes through the CAS patch pipeline, not directly to disk. That keeps the merge in the same audit trail as an agent’s patch.

Comments on a hunk

Every hunk has a comment box. A note is sent back to the hunk’s author as a turn; the patch itself is never edited by the comment. The author answers with a new patch, which appears as a new row in the same conflict history.

Subagent worktrees

A Subagent worktrees block lists every writable child with its approved plan and its stored merge verdict: reviewer, reason, diff hash and any override. A merge that went over a block is marked as one.

The patch journal

Patches are not written with a hopeful writeFile. The sequence is:

  1. Compare the file’s current hash with the hash the patch was built against (CAS).
  2. Append the intended write to the write-ahead journal.
  3. Write the new content, fsync, rename into place.
  4. Mark the journal entry applied.

Apply is idempotent: replaying a journal that already landed does not write twice. Revert is available once per applied patch, and is itself a journaled operation.

On resume the journal is reconciled without applying anything that was not already applied. A half-written patch is visible as a journal state, not as a mystery diff.

Writable subagents, end to end

Write mode gives a child its own worktree, a claim on each assigned file and the full tool set scoped to that list. Three writable children can run at once (D113), and each child’s plan is approved or skipped with a reason before it starts (D114).

Its work does not land by copying files back. merge_subagent reviews the diff with clean context, stores the verdict, and merges through the CAS journal. A blocking reviewer runs on every writable merge; an override needs a typed reason and is recorded beside the verdict (D115).

  • The worktree must still hold the exact diff that was judged, by hash.
  • An approved review merges in one click.
  • A blocked review requires a reason before the same click is offered.
  • The merge is written into the transcript as a note in the user’s voice, and the next turn restates it in the preamble so the parent knows the tree moved.

Commands and tools

Command or tool Does
rigel claim list Lists live, stale and released claims with their owners and clocks.
rigel claim release Writes a release tombstone for a path.
rigel who Shows who is in the room and what each one claims.
rigel snapshot list Lists destructive-command snapshots with their refs.
rigel snapshot restore Restores a named snapshot, journaling the restore.
rigel doctor Checks stale claims and journal state alongside the rest of its integrity rows.

Limits

  • Claims are advisory. They do not prevent a write and are not an OS lock.
  • Staleness is reported, never auto-released. A stale row stays until someone releases it or the 24-hour expiry applies.
  • A merge needs the exact diff hash that was reviewed. If the worktree moved, the merge is refused rather than re-reviewed silently.
  • The watcher polls at 250 ms. A change that lands and is reverted inside one interval can be missed; the journal is still the authority for patches Rigel applied.
  • Comments on a hunk produce a turn. They do not edit the patch, and they do not resolve a conflict on their own.
