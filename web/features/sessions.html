Sessions: a room, a roster, a record.

A session is the unit that owns agents, turns, approvals, patches and money. Close the window and it keeps running in the tray; reopen the project and it reconciles the journal before it lets you continue.

What a session owns

Everything that happens in the window is written to the open project’s SQLite database: the session row, each turn, the agent that produced it, tool results, patches, usage rows, claims, bookmarks and the approval questions. That is why the transcript survives a restart and why the bill can be read per agent rather than reconstructed from memory.

A session also owns its working tree checkpoint. On resume, Rigel compares the tree hash with the checkpoint it recorded. If they differ, it says so instead of pretending the session is still in the state it left.

The roster

The left rail lists every agent in the session with its role, status and model. Add one with the manual + agent form, or start a subagent and watch its row appear as soon as its turn starts.

  • Model and effort per agent. The picker merges the current provider’s roster with OpenRouter’s full list, tags every row with its door, and switches provider when you pick a model from another one. A stored key is the permission to use a door.
  • Swarm. A task typed into the room is sent to the agents you have ticked, not to every row. The button wakes the room; it does not create a second message path.
  • Subagents. A writable child gets its own worktree and its own bill. The parent can chat_send and chat_wait with it while it runs, then collect it with subagent_results.

The roster is not a queue. Two agents can hold the same model and different roles, and the role gutter in the transcript keeps their lines apart.

The transcript

The transcript is a document, not a chat log. Each turn is an article with a role gutter, streaming text, collapsed tool lines and rendered patch diffs. A raw/debug toggle opens the underlying rows when you need to see what the renderer received.

The gate inside a turn

A turn does not run commands silently. run_command shows the exact text, the working directory and the timeout before anything starts. The prompt carries four scopes, matching the CLI’s approval modes.

  • Once approves this invocation only.
  • Session approves the same command for the rest of the session.
  • Always persists the approval in the project’s rules.
  • Deny refuses it and records the refusal on the turn.

Destructive commands take a longer path: a deterministic classifier maps them to policy rows such as delete-outside-project, recursive-remove, force-push, git-reset and registry-write. The prompt names the row and the token that matched, and three read-only advisors get one round before the question is shown. Their answers cannot allow, deny or alter the gate; they are advice attached to it.

Before an approved destructive command runs, Rigel captures a snapshot: a git stash create object kept alive by refs/rigel/snapshots/<id> plus raw copies of changed and untracked files. A non-git tree, or a repository with no commit, is copied whole. The cap is 2,000 files or 200 MB and the capture refuses above it rather than truncating silently.

Resume and close

Closing the window hides it to the tray; it does not stop the session. Running agents and PTYs keep working, the tray reopens the window, and Quit from the tray reaps every child. If the tray cannot be built, Close keeps its ordinary meaning.

Resume is deliberately conservative:

  1. The tree hash is compared with the session checkpoint.
  2. Any turn still marked running is closed as cancelled.
  3. The patch journal is reconciled without applying anything new.
  4. Forcing a continue is recorded as an intervention, not disguised as a normal turn.

A dismissible card reports what happened while the window was out of focus: turns finished, patches applied, approvals waiting and spend since focus. It adds no second notification path.

The session list

The Session pane switches between Sessions and Agents. The list filters by text and status, hides archived rows behind a toggle, and edits in place.

  • Rename in one line, up to 120 characters; blank restores the automatic title.
  • Pin sorts a row first, ahead of newest-first.
  • Archive hides it from the default list but never deletes it. session_list still returns it, the palette still searches it, and it stays resumable.

Pinning and archiving are migration 0012_session_list; bookmarks are 0013. The ledger keeps the row either way.

Templates

.rigel/templates.json holds a per-project shape: model, effort, steps, roster, pinned skills and a prompt skeleton. + session offers the templates, and "save template" stores the current session’s shape, including each pin’s body hash. Writes are atomic, the file is capped at 40 templates and it is never committed. A template written before pin support still loads.

Changed pins

A pin is a body hash, not a floating reference. When the shelf's indexed body moves, the session's pinned list shows a changed badge. Opening it reads both bodies from the content-addressed index and shows a line diff; Keep pin leaves the session on its recorded version, and Update moves it to the current one. Either decision is recorded on the session as a skill_pin intervention with its reason. A disappeared body is reported as unavailable rather than silently replaced. The composer Skills button shows how many pins moved, and the Skills menu can filter to changed pins and keep or update all of them in one action, recording one shared reason for the batch.

Limits

  • A session is scoped to one project. Switching projects switches the database, the claims and the ledger.
  • The tray is what keeps work alive after Close. Without it, Close quits.
  • Archive is not delete. There is no delete-session button in this surface.
  • Template writes cap at 40 rows and never enter version control.
  • A keyboard-only walk of the full exit test is still open, even though focus order and reduced-motion rules are implemented.
