# Rigel content CMS

Payload is the content and admin backend for the public website. It is separate from the Rust
desktop app and from the Firebase Authentication/Firestore path used by the web reader. The
public site remains static on Firebase Hosting.

## Local setup

```bash
cd cms
cp .env.example .env
# set PAYLOAD_SECRET and PAYLOAD_ADMIN_PASSWORD in .env
npm install
npm run seed
npm run dev
```

`.env` is ignored by Git; copy the example and replace the placeholders. `npm run seed` creates or
updates the eight FAQ entries and, when `PAYLOAD_ADMIN_EMAIL` and `PAYLOAD_ADMIN_PASSWORD` are set
in `.env`, creates the first admin user. Open `http://localhost:3000/admin` and sign in with those
values.

The local database is `cms/cms.db` (SQLite). It is ignored by Git. Editing the FAQ collection
changes only CMS data; the website is regenerated by the build below.

## Admin branding and the Firebase link

The admin is Rigel's, not Payload's: the login screen carries the Rigel mark and wordmark, the
navigation uses the compact mark, the title ends in `· Rigel`, and `custom.scss` sets the ink
surfaces and the single amber accent from the product. The favicon is `public/rigel.svg`, copied
from `web/rigel.svg`.

The navigation and dashboard link read-only to the Rigel Firebase console — overview, Realtime
Database, Authentication, Hosting and Firestore rules — for project `rigel-25128`. Set
`RIGEL_FIREBASE_PROJECT_ID` to point those links at another project; the CMS stores no Firebase
credential. The custom pieces are server components in `src/components`, wired through
`admin.components` in `src/payload.config.ts`. After changing them, regenerate the import map:

```bash
npm run generate:importmap
```

## Website build

```bash
cd ..
RIGEL_CMS_URL=http://localhost:3000 node scripts/build-web.mjs
```

`scripts/build-web.mjs` fetches published FAQ entries from `/api/faqs`, renders the Markdown
answers and replaces the marked FAQ navigation and sections in `web/faq.html`. If the CMS is not
running or `RIGEL_CMS_URL` is unset, the build keeps the checked-in FAQ as a static fallback, so a
Firebase deploy never depends on the CMS being online.

The public API exposes only published FAQs; create, update and delete require an authenticated
admin session. The CMS does not write to Firestore and the website's CSP does not need a runtime
connection to it.

## Hosted admin

SQLite remains the local authoring database. For a hosted admin, set `DATABASE_URL` to a Postgres
URL; the config selects the Postgres adapter automatically. The initial migration is checked in.
Apply it and seed a new database with:

```bash
npm run migrate
npm run seed
```

After changing a collection, create a named migration and commit it alongside the config:

```bash
npm run migrate:create add-pages
```

For a Postgres seed that a production container will use, set `NODE_ENV=production`; a development
seed marks the schema as dev-pushed and makes the next `payload migrate` ask for confirmation.

The production image applies migrations before starting Next. `render.yaml` at the repository root
defines a Docker web service plus a managed Postgres database. Connect that file as a Render
Blueprint, then set `PAYLOAD_PUBLIC_SERVER_URL` to the service URL and provide the initial admin
email and password. The Blueprint's first-deploy hook runs the idempotent FAQ/admin seed.

Media uploads still use local disk. Add object storage before relying on the Media collection in a
hosted deployment; the FAQ content does not need it.

Keep the public site on Firebase Hosting and point `RIGEL_CMS_URL` at the CMS during the build. Do
not commit `cms/.env`, `cms/cms.db`, or any admin password.

For a production-like local run with Postgres instead of SQLite:

```bash
docker compose up --build
# in another terminal, once the database is healthy:
docker compose run --rm payload npm run seed
```
